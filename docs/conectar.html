openrouter · conectar una aplicación

Asistente para dar de alta una aplicación en el servicio y llevarte el código que la conecta. Hace cada paso de verdad contra el servidor que elijas; nada se guarda en esta página salvo la clave de administración, en este navegador. La clave de la aplicación se enseña una sola vez.

0Antes de empezar

  • Un nombre para la aplicación, corto y sin espacios raros: presupuestos, notas, bom. Si tendrá entorno de pruebas y real, son dos aplicaciones: notas-pruebas y notas.
  • Qué servidor. El VPS es producción; Fly es la previsualización. Son dos servicios con dos bases de datos: una aplicación dada de alta en uno no existe en el otro, y las claves no sirven cruzadas. Si la aplicación va a usar los dos, se repite este asistente en cada uno.
  • La clave de administración de ese servidor: el secreto de repositorio VPS_SERVICIO_CLAVE para el VPS o SERVICIO_CLAVE para Fly. GitHub no la enseña nunca; solo la tiene quien la creó. Si se perdió, se genera otra, se guarda en el secreto y se relanza el despliegue (deploy-vps.yml o deploy.yml); las claves de aplicación ya creadas siguen valiendo.
  • Dónde guardar la clave que saldrá en el paso 2: gestor de contraseñas o secreto del repositorio de la aplicación. Nunca en el código, en el navegador ni en un chat.

5El código para tu aplicación

    
Solo cambian dos cosas respecto a la API de OpenAI: la dirección y la clave. Los fragmentos llevan ya la dirección del servidor elegido; la clave va donde pone CLAVE_DE_APLICACION, leída de una variable de entorno o de un secreto, nunca escrita en el fichero.

    

    

      

      
    

    

  


  
  

    
6En el repositorio de tu aplicación

    
Lo que hay que dejar hecho para que la conexión sobreviva al primer despliegue y al primer fallo. Es lo que se aprendió conectando la primera aplicación real.

    
Secretos y variables

    
    
      
  • Secreto de repositorio LLM_API_KEY con la clave del paso 2. El workflow de despliegue lo vuelca al servidor (flyctl secrets set o el .env del VPS) y lo quita si el secreto desaparece, para que retirar la clave sea quitar el secreto y redesplegar.
    • 
      
  • Variable opcional LLM_BASE con la dirección del servicio; sin ella, la que lleve el código por defecto. Así se cambia de Fly al VPS sin tocar código.
    • 
      
  • Variable opcional LLM_MODELO. Sin ella, el modelo por defecto del servicio, que es el barato y suficiente para casi todo.
    • 
    

    
Reglas en el código

    
    
      
  • La clave vive en el servidor de la aplicación. Si la interfaz corre en el navegador, el navegador llama a tu backend y tu backend llama aquí. Una clave en el navegador la tiene cualquiera.
    • 
      
  • Aísla al proveedor en un módulo (llm.rs, llm.py…) con una función de negocio, no una de HTTP: titular(texto), mapear_columnas(filas). Si el servicio cambia, se toca ese fichero y nada más.
    • 
      
  • La aplicación funciona sin la clave. Sin LLM_API_KEY arranca igual, lo avisa por el log y /salud lo declara. Guarda primero, pide a la IA después, y si la IA falla, tarda o no está, lo guardado se queda como está y se reintenta luego. La IA nunca hace perder datos.
    • 
      
  • Un tiempo de espera corto en la aplicación (8 s para algo interactivo) y largo en el cliente de lotes (más de 120 s): el servicio concede 120 s a OpenRouter, y el que corta tiene que ser el servicio, que anota la llamada.
    • 
      
  • X-Operacion en cada llamada con el trabajo de negocio al que pertenece. Después, GET /v1/uso/resumen?agrupar=operacion dice cuánto costó cada uno.
    • 
      
  • Guarda X-Uso-Id de cada respuesta junto al resultado: es el registro con tokens, coste y latencia, consultable en GET /v1/uso/{id}. Y si llega X-Presupuesto, enséñala.
    • 
      
  • Salida estructurada con response_format y esquema, max_tokens, y temperature baja si la tarea no es creativa. Lo que devuelva el modelo se normaliza antes de guardarlo: comillas, puntos finales, repetidos, valores que no distinguen nada.
    • 
      
  • Reintentos: dos como mucho, con espera creciente (2 s, 8 s). Cinco peticiones idénticas en un minuto disparan 429 bucle, aunque cada intento fuera legítimo.
    • 
      
  • Sin stream: true hasta que exista: responde 400 streaming_no_disponible.
    • 
    

    
Verificación en el despliegue

    
    
      
  • Con clave: una llamada real tiene que volver bien. Cuesta una fracción de céntimo y es la única forma de saber que la cadena entera funciona.
    • 
      
  • Sin clave: /salud tiene que declararlo y la aplicación tiene que seguir funcionando.
    • 
      
  • Lo que la verificación cree, lo borra pase lo que pase.
    • 
    

    

      
Protege la API de tu propia aplicación. Si tu backend acepta peticiones sin autenticar, en cuanto llame a un modelo cada petición ajena gasta dinero real. Los topes del paso 3 acotan el daño, pero el token de acceso de tu aplicación deja de ser opcional el mismo día que conectas la IA.

    

  


  
  

    
7Si algo falla

    
Primero, saber de quién es el fallo. Un servicio caído y una aplicación que no llama se parecen mucho desde fuera.

    
    
      
  1. /salud del servidor elegido: si responde con el build, el servicio está vivo.
    2. 
      
  2. La consola con la clave de la aplicación: si «Hablas como» dice su nombre y «Di hola» contesta, la clave y el servicio funcionan y el fallo está en tu código.
    3. 
      
  3. Si la consola falla, el código de error de abajo dice qué es.
    4. 
    

    

      
HTTPcodeQué hacer

      
        
401sin_clave, clave_invalidaConfiguración: la clave falta, es la de otro servidor o la aplicación está dada de baja. No reintentar.

        
402presupuesto_agotadoParar y avisar. No reintentar hasta el siguiente periodo o hasta que administración suba el tope.

        
429cuota_superadaEsperar un minuto y reintentar.

        
429bucleAlgo repite la misma petición. Parar: es un bug, no una carga.

        
400cuerpo_invalido, streaming_no_disponiblePetición mal formada o stream: true. Corregir.

        
403solo_administracionRuta de administración con clave de aplicación. Es normal: la aplicación no debe tocarla.

        
502openrouter_rechaza, openrouter_inalcanzable, openrouter_tardo_demasiadoFallo del proveedor; con openrouter_rechaza, error.upstream trae su cuerpo. Reintentar una o dos veces con espera creciente.

        
503sin_configurarEl servicio no tiene sus claves. Avisar a administración.

8Después

    
    
      
  • Ver el gasto: en la consola con la clave de administración, panel Aplicaciones; o desde el PC, tools/apps.ps1 -Gasto. Con la clave de la aplicación, GET /v1/uso y /v1/uso/resumen devuelven solo lo suyo.
    • 
      
  • Revocar: «Dar de baja» en la consola o tools/apps.ps1 -Baja <id>. Desactiva, no borra: el histórico sigue diciendo quién gastó.
    • 
      
  • Rotar la clave: crear una aplicación nueva con el mismo nombre y sufijo, cambiar el secreto en el repositorio de la aplicación, redesplegar, y dar de baja la vieja cuando el despliegue esté verde.
    • 
      
  • Subir el tope: consola, botón «Topes» en la fila de la aplicación. No hace falta redesplegar nada.
